# C3 Life server installer

Sets up the C3 Life server (Dell OptiPlex Micro, Windows 10 IoT Enterprise LTSC 2021) and installs C3 Life on it. It goes with the **C3 Life server set-up guide**. The scripts do the Windows parts of the guide for you, so you don't have to click through every setting.

## What's in the folder

| File | What it does | Changes things? |
|---|---|---|
| `Setup-C3LifeServer.ps1` | Windows settings (guide Steps 3 and 4): PC name, fixed booth address, Private network, Energy Efficient Ethernet off, power and sleep, fast start-up off, UPS shut-down, Windows Update policies, no Windows tips | Yes. It shows the list and asks first |
| `Install-C3Life.ps1` | C3 Life (guide Steps 5 and 6): copies the server and app to `C:\C3Life`, starts C3 Life when **booth** signs in, adds firewall rules for the booth network only, starts DVS and the full-screen booth screen at sign-in, and checks the other software is installed | Yes. It shows the list and asks first |
| `Check-C3LifeServer.ps1` | Checks everything: OK, CHECK or PROBLEM for each item, saved to `C:\C3Life\logs` | No, it only reads |
| `Uninstall-C3Life.ps1` | Removes C3 Life. Keeps the logs and config unless you add `-RemoveData` | Yes |
| `server\c3life_server.py` | The C3 Life web server (port 80, booth network only). It also checks PINs and keeps each person's monitor mixes in sync on all their devices | — |
| `C:\C3Life\data` (made when it runs) | Everyone's PINs (hashed, never plain) and mixes. Only the booth user and admins can open it. Back it up with the rest of `C:\C3Life` | — |
| `app\` | The C3 Life app. **For now this is the clickable mock-up.** The real app replaces this folder later | — |

## Order

1. **BIOS** (guide Step 1) and **install Windows** (guide Step 2). Make the local users **admin** (Administrator) and **booth** (standard).
2. Sign in as **booth** once, then sign out. This creates its profile.
3. Sign in as **admin**. Copy this whole folder to the PC, for example to `C:\Setup\c3life-server`.
4. Right-click **Start › Windows PowerShell (Admin)** and run:
   ```powershell
   cd C:\Setup\c3life-server
   Set-ExecutionPolicy -Scope Process Bypass -Force
   .\Setup-C3LifeServer.ps1
   ```
   Read the list, then type **YES**. Restart if it asks.
5. Install **Dante Controller**, **Dante Virtual Soundcard**, **R Remote V6** and **Companion** (guide Step 5).
6. Install Python for all users: `winget install Python.Python.3.12 --scope machine`
7. In the same Administrator PowerShell, run `.\Install-C3Life.ps1` and type **YES**.
8. Run **Sysinternals Autologon** and enter the **booth** user and password. Scripts don't store passwords.
9. Restart. The PC signs in as **booth**, and C3 Life opens full screen within about 30 seconds.
10. Run `.\Check-C3LifeServer.ps1` (a normal PowerShell is fine). Fix anything marked PROBLEM.

**Change the PINs and the Admin password.** The first time C3 Life starts, everyone has PIN 1234 (Viewer has none), and Admins sign in with the password `c3life-admin`. Admins use a password, not a PIN: 8 or more characters, with a letter and a number or symbol. Change each one in an Administrator PowerShell (for an Admin it asks for a password):

```powershell
& "C:\Program Files\Python312\python.exe" C:\C3Life\server\c3life_server.py --config C:\C3Life\server\config.json --set-pin "Keys (musician)"
```

Then use **C3 Life server power › Restart C3 Life**. Five wrong PINs or passwords in a row lock that name for 5 minutes.

**Listen** is split in two: the Listen page is just for listening, and **Listen settings** (Admins only) holds Rooms, Groups, Sources, From home and Public. On **Users & PINs** an Admin can set what each person may listen to (extra sources on top of their groups, or kept to one thing only); saving that needs the Admin password again. Sources can take their names from Dante (what's routed into their DVS channels), like the Patch tab. Anyone on the booth Wi-Fi can listen **without signing in** to the groups ticked "Anyone can listen without signing in" (at first the Stream mix, with subtitles made from the speech mics). Helpers who only listen can use the **Listener** account (no PIN); Access levels › Listen sets None / View / Control for each role. **Access levels** are kept on the C3 Life server (`data\access.json`), so every device shows the same ones and the server enforces them for Listen and monitor mixes; changing them needs the Admin password. **Dante names** are read from the Dante network by netaudio (installed by `Install-C3Life.ps1`, read only), looking for Dante Virtual Soundcard by the computer's name (`C3LIFE`) unless `dante_dvs_name` in `config.json` says otherwise.

**Listen** (other rooms, room players and listening from home). People pick what to hear on the **Listen** page, and Admins set sources, groups and rooms there. It needs:

- **ffmpeg**, installed for everyone: `winget install Gyan.FFmpeg --scope machine`. Then run `Install-C3Life.ps1`, which finds ffmpeg and the Dante Virtual Soundcard sound device by itself.
- **Dante Virtual Soundcard** set to 16 × 16, with the listening sources routed to DVS 4 onwards (guide Step 5).
- **To listen from home:** install Tailscale on the C3 Life server, sign in with the church account, then run `Install-C3Life.ps1 -ListenFromHome`. From home, people can only open Listen and hear what a group with *Can listen from home* allows. **Never** turn on subnet routes or an exit node for the C3 Life server in Tailscale.

- **Remote support (fixing things from home):** run `Install-C3Life.ps1 -RemoteSupport` (Tailscale installed and signed in first). An **Admin** who signs in through Tailscale then gets the whole app, with a purple *Remote support* label on every screen; everyone else from outside still gets Listen only. Each remote sign-in and page is logged. It also turns on Tailscale's *Run unattended*, so the PC reconnects after a restart with nobody signed in. For the desktop itself, set up **Chrome Remote Desktop** (free, works on Windows 11 Home or Pro, shows the real booth screen so it stays visible in the booth, Google account plus a PIN of 6 or more digits). Not recommended: Windows Remote Desktop (Pro only, and it locks the booth screen while connected), TeamViewer and AnyDesk free (they block church use as commercial). Tailscale's free plan has 6 users; ask Tailscale whether church use is fine, or use its 50% charity discount.
- **Subtitles:** `Install-C3Life.ps1` installs Vosk for Python and downloads the English speech model (about 40 MB) to `C:\C3Life\speech-model`. That needs the internet once; after that, subtitles are made on the C3 Life server with no internet. Turn them on per source on Listen settings › Sources (on for Pastor and speech mics). Use `-NoSubtitles` to skip them. Every line is also saved to `C:\C3Life\data\transcripts` (one file per day and source), so subtitles carry on after a restart and an Admin can download them on Listen settings › Sources. They're deleted after 30 days. An Admin changes that on Listen settings › Sources › Saved subtitles (don't save, 7, 30, 90 days or a year), and can delete a day there; `transcript_days` in `config.json` is only the starting value.
- **Translated subtitles:** listeners choose a language under Subtitles. Each line is translated on the C3 Life server by Argos Translate, with no internet. `Install-C3Life.ps1 -Languages es,fa,zh` downloads the language packs (about 100 MB each) to `C:\C3Life\translate`; the default is Spanish only. Run it again with more codes to add languages. Codes: es Spanish, fa Persian, zh Chinese, ar Arabic, fr French, pt Portuguese, ko Korean, hi Hindi, ur Urdu, ru Russian, uk Ukrainian, tl Tagalog, sw Swahili, and [more](https://www.argosopentech.com/argospm/index/). Computer translation gets things wrong at times, especially Bible verses and names.
- **Public feed (optional):** an internet radio account with Icecast (for example Caster.fm, Radio.co or your own server). An Admin fills in the details on Listen settings › Public and changes the public link there whenever needed. The C3 Life server sends one stream out; nothing comes in from the internet. It only starts when someone presses Start. The password is kept on the C3 Life server and never sent back to any screen.
- **Hearing aids:** nothing to install. Hearing aids paired with a phone play Listen straight into the aids. In the main hall use a hearing loop instead, because of the delay.

The audio is about 1 to 3 seconds behind the room, and keeps playing on a phone with the screen locked. A stream only runs while someone is listening to it.

**Name tags (lower thirds).** Each week C3 Life reads the plan's **9 - Ministry** team in Planning Center (Welcome, Prayer, Pastoral, Offering, Preach, Close and the Meeting Leader), links each position to its item in the plan, and matches each name to the ProPresenter prop with the same name (e.g. a prop called `Chris Denham`). Anyone without a prop, such as a guest or a couple, goes into one ProPresenter message called `Name tag` with a `Name` text token. When 9 - Ministry says *Guest Preacher*, the name in the item's *Hosting* note is used. They're checked on **Running order › Name tags** (where a name can be typed for one week, and an Admin can change which item goes with each position) and shown with one tap on **Show**; nothing goes on screen by itself. It needs:

- A Planning Center **Personal Access Token** (api.planningcenteronline.com › Personal Access Tokens, read access to Services). Run `Install-C3Life.ps1 -PlanningCenterAppId <id> -PlanningCenterSecret <secret>`. It's kept in `config.json` on the C3 Life server and never sent to phones. Planning Center is read every 15 minutes; with no internet the last good read is kept.
- ProPresenter 7.9 or later with **Settings › Network › Enable Network** on, port 50001. The network scan finds it by itself (and follows it if its address changes); to set it by hand, `-ProPresenter http://<address>:<port>`.
- Other settings in `config.json`: `pco_service_type` (`Sunday Morning`), `nametag_team` (`9 - Ministry`), `nametag_note_categories` (`["Hosting"]`), `nametag_message` (`Name tag`) and `nametag_token` (`Name`).

**Bible Scripture** (Show › Bible, and on Home). Type a passage (`john3:16`, `John 3:16-18`, `1 Cor 13:4-7`, `Psalm 23`), pick a version and a look, check every slide in the preview, then add it to a ProPresenter playlist (it asks first). That adds a line called *Scripture: John 3:16 (NIV)* where you chose (it starts after *Bible Scripture*). On the day, **Show**, **Next slide** and **Hide** put each slide on screen; nothing goes on screen by itself. ProPresenter's network API can't make slides, use ProPresenter's own Bibles or apply a theme, so:

- **Looks** are ProPresenter messages whose names start with `Scripture` (e.g. *Scripture - Full screen*, *Scripture - Lower third*), each with text tokens `Reference` and `Text`, styled with the theme you want. Make them once in ProPresenter.
- **Versions.** KJV and the World English Bible British Edition (WEBBE) are public domain and built in (`server\bibles`, no internet). ESV needs a free key from api.esv.org (`-EsvKey`, non-commercial use). NLT needs a key from api.nlt.to (`-NltKey`). NIV belongs to Biblica: the church needs permission and an API.Bible account that includes it (`-ApiBibleKey … -NivBibleId …`). Keys stay in `config.json` and never reach phones. Bibles bought inside ProPresenter can't be read from outside it.
- Up to 60 verses at a time; long verses are split into slides of about 220 letters (`scripture_slide_chars`). Added passages are kept for 14 days.

**Slide cues** (Mixer › Cues). Sound changes when ProPresenter puts a slide live. Each cue says *when* (a presentation, a slide group such as *Chorus*, or a slide label), *what* (channels on or off, faders to a level, each with a fade time: on fades in, off fades out, and one fading out while another fades in is a crossfade) and *how* it runs: a countdown with Cancel and Run now (5 seconds unless the cue says 3 or 10), ask first, or straight away with Undo (Admins only). Only Admin and FOH sound see the countdown. **Run check** reads ProPresenter's current playlist and says which cues will run; **Check and save** runs it first and the C3 Life server refuses to save cues that can't work. Cues are kept in `data\cues.json`. With the Wing connected and set to Control they move the desk itself (the fades run on the C3 Life server, so they finish even if a phone locks, and Undo puts the desk back); on Watch only they move the app's mixer.

**Report an issue** (in every screen's menu, for everyone in the building). A subject, what happened, who is reporting and up to 4 photos (made smaller on the phone). The C3 Life server keeps each report in `data\reports` and emails it on its own (photos attached) as soon as there's internet, trying every minute and carrying on after a restart. Set up email with `Install-C3Life.ps1 -SmtpHost smtp.office365.com -SmtpUser booth@yourchurch.org` (it asks for the password, which stays in `config.json`). An Admin sets where reports go on the page and can change it any time; each report can also go to a different address. *Send from this phone instead* uses the phone's own share sheet (email or messages with the photos, over mobile data). Optionally each report is also added to a **monday.com** board: `-MondayToken …`, then the board id on the page.

**Planning Center account, timers and time zone.** On Running order an Admin sees who is signed in to Planning Center, can sign out (it asks first) or switch account by typing a Personal Access Token (checked with Planning Center first, kept in `data\pco.json`, never sent to phones), and picks the service type. Show has **Planning Center timers**: the service and band-call times count down, **Now** shows the item happening now with its timer (start, stop, reset, ±1 and ±5 minutes, set, the same on every device) and **Up next** previews the next item and about when it starts; *Next ›* and *‹ Previous* move along only when tapped, and the rest sit under *All items* (jump to one, or change its time) so it isn't one long list. Either timer card (Planning Center or ProPresenter) can be hidden per device. In any item, *Change its length in Planning Center…* changes the item in Planning Center itself after asking. Planning Center sends times in UTC; C3 Life shows them in the C3 Life server's time zone (the booth network's), whatever region the account is set to, and says if they differ.

**The Wing, live** (Mixer). The C3 Life server talks to the Behringer Wing over the booth network: names, colours, faders, pans, mutes, each channel's mic input with its gain and 48 V phantom power, and the meters (left and right for stereo inputs). It uses the Wing's OSC server (UDP 2223) for values and the Wing's native protocol (TCP 2222, then UDP) only to ask for meters. Set the Wing's address with `Install-C3Life.ps1 -WingIp 192.168.10.20`, or on the Mixer screen (*Find the Wing on the network*). It starts as **Watch only** (reads the desk, sends nothing); an Admin switches it to **Control** on the Mixer screen, which asks first. Faders, pans, mutes and gain then move straight away (a fader jump bigger than 6 dB asks); phantom power and renames always ask. The Wing gives one OSC subscription at a time, so C3 Life also asks for every value every few seconds and stays right alongside Mixing Station or Co-Pilot. The mode and address are kept in `data\wing.json`. The installer opens UDP for the Wing's meters, booth network only.

**Mixer strips.** The Mixer opens as strips, like a desk (and Mixing Station): coloured name, pan, MUTE, level, a fader with its scale and meter (two meters on stereo inputs). Faders move from where you grab them, so a touch never makes one jump; *Fine* moves them a quarter as far, and *Mute enable* stops stray mutes. Layers: Channels, DCAs, Buses, Aux, Main, Matrix, and your own (*+ Layer*: a name and the strips you tick, in that order). As many strips show as fit: about 8 on a phone upright, 14 or more sideways, around 20 on an iPad or laptop; *Layout…* sets the strip width or shows a list instead. Layers and layout are kept on each device. Tap a strip's name for its gain, phantom power, rename and fader lock.

**Channel EQ, gate and compressor** (Mixer, tap a channel's name). Four tabs: *Input* (gain and phantom power, polarity, trim, the Wing's low and high cut), *EQ* (a curve with six points to drag: low shelf, four bands, high shelf; or pick a band and use − +), *Gate* (opens above, turns down by) and *Comp* (starts at, ratio in the Wing's own steps, make-up gain, attack and release or Auto). Each says in plain words what it's doing. **EQ** can show the Wing's RTA (120 bands, 1/12 octave from 20 Hz, before or after the EQ) behind the curve: it points the Wing's own RTA at the channel (`/cfg/rta/rtasrc` and `rtatap`, read back from `$src`), so the desk's RTA screen follows, and it needs Control. **Gate** and **Comp** look like FabFilter Pro-C: the last 8 seconds of the level going in and coming out with the gain reduction hanging from the top, the threshold, the curve with a dot where the sound is now, IN/OUT/GR meters, and knobs (drag up or down, Fine, arrow keys). The level and gain reduction come from the Wing's channel meters (8 values a channel: input, output, gate key and gain, dyn key and gain; 256 is 60 dB for the gate and 20 dB for the compressor), kept on the C3 Life server for the channel someone has open. They're the Wing's standard models (STD EQ, GATE, COMP); a channel using another model (SOUL, EVEN 88…) says so and offers on and off only. The C3 Life server only reads a channel's processing while someone has it open (about 40 values, every second), so the Wing isn't flooded. Changes need Control, like faders.

**Tio1608-D** (Mixer › Tio1608-D card, and a Tio channel's Input tab). C3 Life changes the Tio's gain (−6 to +66 dB), 48 V phantom power and low cut on each input itself, with the same Yamaha text protocol R Remote and Yamaha desks use (TCP 49280: `set IO:Current/InCh/HAGain 0 0 30`, and NOTIFY lines when R Remote changes something, so both stay in step). Set the address with `Install-C3Life.ps1 -TioIp 192.168.10.41` or on the Tio card. It starts as **Watch only**; an Admin switches it to Control (it asks first), and phantom power always asks. Tio input 1 is taken to arrive on Wing card input 1 (changeable on the card) so the right channel shows the Tio's gain. The commands come from the Tio's own parameter list as published with the Bitfocus Companion Yamaha module; **they haven't been tried on our Tio yet**. Settings are kept in `data\tio.json`. R Remote keeps working alongside it.

**Monitor mixes on the Wing** (stage 3). *Sends on faders:* on Mixer, *Faders show* turns the strips into every channel's send to one bus (level, ON and, when pan link is off, pan), read and changed on the Wing (`/ch/N/send/B/...`). *My mix* is the musician's own bus on the Wing when it's in Control: their faders (with their MCA groups) are the sends, ON is the send on, and their volume, MUTE and pan are the bus's fader, mute and pan; what FOH changes comes back to their screen within a couple of seconds, and the Wi-Fi icon says whether it's live. Who has which bus is kept on the C3 Life server in `data\monitors.json` (monitor buses; each musician's own mix and any extra ones), so the server only lets a musician change their own mixes, and the FOH lock (*Musicians can change their own monitor mix*) is enforced there too. *Musician mixes on the Wing* checks every monitor bus on the Wing for sends that aren't Pre or are pan linked, by name, and fixes them after asking.
- **The click** (Wing Aux 4) in My mix is Aux 4's send to the musician's bus (`/aux/4/send/B/...`): its fader, ON and pan, both ways, the same as a channel.
- **My mix's EQ** is the musician's bus's own EQ on the Wing (`/bus/B/eq/...`), the same as FOH sees on the desk. On the Wing it uses these bands:
  - **Low cut:** the low band set to Cut (off: a flat shelf).
  - **Low:** a broad band 1, because the low band is the cut.
  - **Low mid** and **High mid:** bands 2 and 3, with Wide, Mid or Narrow.
  - **High:** the high shelf.

  Bands 4 to 6 are left as FOH has them.
- **Both ways, and what it changes:** what FOH changes on the desk comes back to the screen, with frequencies shown as the nearest one on the screen's list. The first EQ change on a bus sends the whole EQ, so the desk then matches the screen exactly. It changes the bus's EQ for whoever listens to that mix. The lock and "only your own mixes" apply to the EQ too.
- **RTA behind My mix's EQ** (the RTA button on My mix › EQ), like the channel EQ on Mixer. It points the Wing's own RTA at the musician's bus, after its EQ, and draws it behind the curve. It asks first, because the desk's RTA screen follows. A musician may only point it at their own mix, and not while mixes are locked. They only see the RTA while it's on one of their mixes; if FOH moves it, My mix says so.
- **Tap EQ** (the TAP EQ button on My mix › EQ, and `GET/POST /api/wing/tapeq`). This is each channel's own 3-band EQ on the Wing's pre-fader send tap (`/ch/N/peq/...`), so it changes what the in-ears hear without touching front of house.
  - **It belongs to the channel, not to one mix.** A change is heard in every monitor mix that takes that channel pre-fader, and the panel says so.
  - **Its own access level, Tap EQ:** Admin and FOH sound have Control; musicians can look. An Admin can give Control to any role (a worship leader, say) in Access levels. Mixer control alone isn't enough: changing a tap EQ field through the Mixer needs Tap EQ control too.
  - **Not tried on our Wing yet:** the field names come from the Wing OSC document (V0.3.2). The tap point itself (`ptap`) is read but not changed.
- **The RTA's source number for a bus is a guess:** the Wing numbers every strip in one list. Channels are 1-40 (checked by reading it back), and buses are taken to come after the 8 aux inputs (bus 1 = 49). That's how the Wing orders its strips, but it hasn't been tried on our Wing yet. The screen reads the source back and says when it isn't the mix it asked for.

**Opening the app.** Typing the C3 Life server's address (for example `http://192.168.10.10`) opens **Listen**, so anyone can listen straight away, with **Sign in** at the top right (as on Home). After signing in, each person goes to their own first screen: Home for the booth team, My mix for musicians, Foyer for the foyer team. Someone already signed in on that phone or iPad goes straight there when they type the address. (`"start_page": "/player.html?p=Listen.dc.html&start=1"`; an older `c3life.json` that still says `Main.dc.html` keeps opening Home until it's changed.)

**Team chat for each person.** In Users & PINs an Admin ticks or unticks *Can use team chat* for each person. Listeners don't have chat unless it's turned on. With it off, Chat disappears from that person's menu on every screen, and opening Chat says it's turned off. Chat itself, and Users & PINs, still work inside the app on each device (they aren't on the C3 Life server yet), so this setting is too.

**Where the RTA listens** (RTA › Where the RTA listens; FOH sound or an Admin). The room mic can come from anywhere: any Wing input (local, aux, AES50 A/B/C, card, USB), a Tio1608-D input sent straight onto Dante without going through the desk, or another Dante device. The desk reference (what the desk sends, to compare the room against) can be any main, bus or matrix. Each one reaches the C3 Life server by Dante Virtual Soundcard (channel 1-64), AES67 (1-8) or Wing USB (1-48). It's kept on the C3 Life server (`data\rta_inputs.json`, `GET/PUT /api/rta/inputs`). Either one can be **mono or stereo**: in stereo the left and the right each have their own source and channel, from anywhere (a main, bus or matrix is picked as its L and R side, `"MAIN/1"` and `"MAIN/1/R"`). The desk reference can also have the **subs added**, always stereo (subs left and subs right from any main, bus or matrix, on their own channels), so the room is compared with mains and subs together. No two of them can share a channel. **Choosing doesn't change the desk or Dante**: C3 Life listens on the channels you pick. Under each one are the steps to set on the Wing and in Dante Controller, and for Dante Virtual Soundcard the route Dante really has (read with netaudio), with a tick when it's there. The Wing's own RTA, on a channel's EQ, works too.

**The RTA screen** looks like a phone analyser app. Along the top: Play/Pause, compare with the desk reference, ID (marks the loudest frequency), Ring-Out (the feedback watch, marking a ringing note on the graph) and the RTA settings. The RTA tab is a 1/12-octave spectrum (green, with a red peak hold, two handles to move the top and bottom of the scale), the 1-minute and 15-minute Leq with dB(A) in a box on the graph, and a spectrograph underneath drawn as one small picture so phones and iPads stay smooth. The SPL tab has the level in big numbers, the 1m, 15m, 30m, 1h and 8h Leq, a history with Start/Reset and min, max and average, and Limit Guard (the level alert). Off the RTA tab the screen updates once a second, so taps always land. The analysis on the C3 Life server isn't built yet, so the spectrum and levels are still the mock-up's.

**The room-mic RTA** (the RTA screen, and the RTA bar along the bottom of every screen). The C3 Life server listens to the channels chosen above, using ffmpeg like Listen does. It only listens while a screen is asking, and stops 30 s after the last one stops.
- **What it works out:**
  - the room mic's spectrum in 120 bands (1/12 octave from 20 Hz), and the desk reference's;
  - the room level in dB(A) and dB(Z);
  - the Leq averages from 1 minute to 8 hours. They're kept on the server, so every phone and iPad shows the same history.
- **Stereo and subs:** a stereo mic is the mean of left and right. The reference adds the subs when they're on.
- **The reference's level:** the desk reference is digital, so it's moved up or down to sit on the room's curve (matched between 250 Hz and 4 kHz). Its shape is what you compare.
- **No numpy needed:** plain Python does a 4096-point analysis five times a second. That's about 15% of one core while someone has a screen open.
- **Calibration** (Calibrate):
  - a 94 dB calibrator (**Calibrate to 94.0 dB**), or **Match** a sound level meter's dB(A);
  - kept in `data\rta_live.json`, and **Clear the calibration** goes back;
  - until it's calibrated the levels are an estimate (0 dBFS = 120 dB SPL), and the screen says so.
- **When it can't hear the room:** with no sound on the channel, ffmpeg missing or Dante Virtual Soundcard stopped, the RTA says why and shows no spectrum or level. It never shows made-up ones. In the preview (no server) the demo runs as before.
- **The API:** `GET /api/rta/live` (RTA view), `POST /api/rta/calibrate` (RTA settings control).
- **Still to do:** Ring-Out (the feedback watch) still uses its demo.
- **Not tried with a real mic, DVS or calibrator yet.** The Wing USB device name (`rta_usb_device`, default `WING USB Audio`) is a guess.

**RTA settings** is an access area of its own (Access levels), after Listen: where the RTA listens, Set it up for me, the level alert and the feedback watch. Admin and FOH sound have Control; ProPresenter, Lighting and Viewer can look; everyone else doesn't see the settings. A saved `access.json` from before keeps every level and gets these defaults for the new area. `PUT /api/rta/inputs` and Set it up for me need RTA settings: Control.

**Set it up for me** (RTA › Where the RTA listens). C3 Life can also do the patching: it works out what's needed for the room mic or the desk reference, shows it from what to what, and only after Yes makes it. On the Wing that's a Dante card output (one that already sends that source, or the first that's Off) or a USB output, sent as `/io/out/CRD/n/grp` and `/in`; on Dante it's the route into the C3 Life server's DVS channel (`netaudio subscription add`, replacing what that channel had). Each change is read back; if one doesn't take it stops there, and *Put it back* undoes it. The Wing part needs the Wing in Control and *Wing patch* control; the Dante part needs *Dante* control (an Admin). If the Wing or Dante changed since you looked, it stops and shows the new plan. A Tio input goes straight from the Tio to the server on Dante. AES67 flows are left to Dante Controller. **Not tried on our Wing and Dante yet**: the Wing's output names follow its input ones, and Wing card output n is taken to be its Dante channel n; the hardware check reads the card outputs first to confirm. Do the first one with FOH watching, not during a service.

**Names on Dante** (Mixer › Dante). Rename a Dante device (letters, numbers and hyphens, up to 31) or a transmit or receive channel (up to 31, no `= . @`). Routes find their source by name, so renaming a device or a transmit channel would break every route from it: C3 Life lists them first, renames it (`netaudio config`) after an Admin says yes, and routes each one again with the new name. When it's the Wing's card, the Tio or C3 Life's own DVS that's renamed, C3 Life keeps the new name (`data\dante.json`) so it still finds them. **Not tried on our Dante network yet.**

**The foyer** (Show › Foyer, and the Foyer team's screen). The foyer's name, its two mixes (two Wing buses) and the matrix to its speakers are kept on the C3 Life server (`data\foyer.json`), so every device shows the same. The two mixes are called what the desk calls those buses, read from the Wing (`GET /api/foyer`, which the Foyer team may read even though they can't open the Mixer). With the desk not connected they say Spotify and Live service. An Admin (Access levels › Foyer setup) can rename the foyer, for example Café. The new name shows on the Foyer screens, the Show tab and the menus. Switching and volume on the Foyer screens are still the mock-up's; they don't move the Wing yet.

**Music** (Show › Music) plays Spotify through a **C3 Life helper** (`helper/c3life_helper.py`): a small plain-Python program for any Mac or Windows PC in the booth with Spotify or ProPresenter. Each helper says what its computer can do:

- **Mac:** everything, with the Mac's own AppleScript: playlists, play and pause, next and previous, volume, what's playing, and fades (they run on the Mac, so they finish even if a phone locks; fade out pauses at the end and puts the volume back for next time). No Spotify developer key, and it works in Offline mode.
- **Windows PC:** Spotify's Play/Pause, Next and Previous, as the keyboard's media keys. Windows has no way to ask Spotify what's playing, pick a playlist or set its volume from outside, so Music says so and greys those out.
- **Both:** open ProPresenter (Music › Open ProPresenter, which asks first), on the computer ProPresenter is set up on.

Nobody types an address:

1. On each computer, install it once from the `helper` folder: **Mac** double-click `Install-Helper.command` (if macOS says it can't be opened: right-click › Open › Open); **Windows** double-click `Install-Helper.cmd` and say Yes when Windows asks. It copies the helper to `~/Library/Application Support/C3 Life Helper` (Mac, a login item through launchd) or `%LOCALAPPDATA%\C3 Life Helper` (Windows, a hidden logon task, plus port 8099 opened for private networks only), starts it, makes it start by itself whenever someone logs in and restart if it stops, and shows its key. No Terminal window stays open. Installing again keeps the key; `Uninstall-Helper` takes it off. (It can also be run by hand: `python3 c3life_helper.py`.) Keep that computer logged in.
2. The network scan finds it: 20 seconds after the server starts, every 5 minutes, or *Find it now* on Music. It's listed under **Computers with the C3 Life helper**, with *Key needed*.
3. An Admin types its key there once. The server checks it with the helper, then keeps it in `data\helpers.json`; it's never sent to phones.
4. If a computer gets a new address, the server follows it by the helper's id, key and all. Through the day the server checks every helper (and the Wing and the Tio) once a minute; anything that stops answering makes it scan straight away (at most once every 2 minutes), so a move is picked up within about a minute. Each helper shows when it last answered.
5. With more than one computer that has Spotify, pick which one plays at *Plays on* (the first one used stays chosen). Add the church's playlists on Music › Change list by pasting Spotify's *Share › Copy link to playlist*; they're kept on the server (`data\music.json`).

The first time a Mac plays, macOS asks whether Terminal (or Python) may control Spotify, and once for ProPresenter: click OK. On Windows, allow Python on Private networks if it asks. `"helper"` and `"helper_key"` in `config.json` (or `Install-C3Life.ps1 -Helper … -HelperKey …`) still set one by hand; it's taken over by the scan once found.

**Music** is an access area of its own (Access levels, after Tap EQ), so FOH can run the walk-in music without also running slides: Admin, FOH sound and ProPresenter have Control (play, change the list, open ProPresenter); Lighting and Viewer can look. A saved `access.json` from before keeps every level and gets these defaults for the new area. Only Admins type or change keys and forget a computer. Only the booth network can reach a helper, and everything but `GET /hello` (which the network scan uses) needs its key. **Not tried with the church's computers and Spotify yet, and the Windows media keys haven't been tried on a real PC**: the tests use a fake Spotify and fake keys, so try it before a service the first time. The foyer's switching and volume are still the mock-up's.

**Finding everything, on any network.** Nothing in C3 Life needs the church's network to be 192.168.10.x. The installer reads the HP's own networks (192.168.x, 10.x, 172.16-31.x) unless `-BoothNetwork` says otherwise, and the firewall rules use Windows' *LocalSubnet*, which follows the PC's network if it changes. Each time it starts, the server also lets in the network it's on now (`"own_network": false` turns that off). The network scan tries each network the server allows (on a big one, the part the HP is in), plus every address Bonjour announces, so Dante devices on their own 169.254.x.x addresses (no DHCP server) are still recognised, the Tio included. What's set up is followed when its address changes: the Wing by its serial number, the Tio and ProPresenter by their network card, each helper by its own id, Lightkey by its Bonjour name. A helper answers any private network, never the internet. Phones and iPads only ever talk to the C3 Life server, so give the HP itself a fixed address (a DHCP reservation on the router), or use `http://c3life.local`.

**A warning on every screen** when something that's set up stops answering for 15 seconds: the Wing or the Tio (they say themselves), ProPresenter (asked once a minute), a C3 Life helper (checked once a minute with its key) or Lightkey (seen or not by the last scan; it doesn't answer OSC). It says since when, what to check, and links to that screen; after 8 seconds it shrinks to a small badge in the bottom corner (tap it for the details again), so it never sits on top of the controls during a service; *Hide for 10 minutes* hides it on that device. Each person only hears about what their role can use (the Wing and the Tio: Mixer or Own monitor mix; ProPresenter: Show; helpers: Music; Lightkey: Lights). Whatever stops answering also makes the network scan run straight away (at most once every 2 minutes), so a device at a new address is picked up within about a minute. Something turned off on purpose, or never set up, isn't a warning. `GET /api/devices`.

**Lights** (the Lights screen, laid out like Lightkey's Live view). Lightkey stays the lighting desk on the lighting Mac. Its fixture library, its Art-Net and sACN output, its cues and its Preset Palette all stay there. C3 Life sends it **OSC** (Lightkey › Settings › External Control › **Enable OSC**, UDP port 21600), so anyone with Lights control can run the lights from a phone or iPad:
- **Live**: Go, Back and Release, the master and Blackout (Lightkey has no blackout message, so the master goes to 0 and then back), Tap tempo, cue tiles, the Preset Palette (tap a preset on, tap again to turn it off), and looks.
- **Program**: moving heads and colour fixtures, with a **fade time** (0 to 60 s). Covers pan and tilt on a pad, intensity, colour, colour temperature, colour wheel, gobo, shutter and strobe, zoom, focus, iris, frost, prism and haze. Everything is sent as a Lightkey *fixture override*: it sits on top of Lightkey's cues until **Give back** clears it. **Save as a look** keeps the picked fixtures' settings and the fade; a look can be fired on its own or brought in with a cue.
- **The fade:** Lightkey's OSC has no fade for fixture settings, so the C3 Life server does the fade itself, sending the new value 20 times a second. Pan, tilt, intensity, colour, colour temperature, zoom, focus, iris, frost and haze slide. Wheel slots, gobos, the shutter and the prism change at the start. A fade starts from what C3 Life last set; a property it hasn't set since the last Give back jumps.
- **Show setup**: the lighting Mac's address (Admin; **Find Lightkey** looks for it over Bonjour), Off or Control (turning it on asks first), which Live page, and whether Go runs C3 Life's cue list or Lightkey's own cuelist (`/live/nextCue`). Also the lists: cues by their Lightkey names, Preset Palette paths like `Movers/Colors/Indigo`, fixtures by Lightkey's short names (like `F4`) with their pan and tilt range, colour wheel and gobos (drag them on the stage to where they hang), and looks.
- **Where it's kept:** the lists in `data\lights.json`, the link in `data\lightkey.json`.
- **What the screen can't see:** Lightkey doesn't answer over OSC, so the screen shows what C3 Life last sent. If someone presses a cue on the Mac, the screen won't know.
- **Access:** Lights view to look, Lights control to fire and program. Only an Admin changes the Mac or turns the link on.
- **Off:** with the link off nothing is sent, and a button says what it would have sent.
- **Not tried on a real Lightkey yet.** The addresses are the ones in the Lightkey User Guide (chapter 15). The first time, open Lightkey's **Window › External Control Log** and press one of each (a cue, a preset, the master, a programmer change). Check that the colour wheel and gobo numbers land on the right slot, because the guide doesn't say whether the first slot is 0 or 1.
- **MIDI from MultiTracks Playback** (Lights › Show setup › MultiTracks Playback).
  - **The session:** the C3 Life server is a network MIDI session called "C3 Life" (Apple's RTP-MIDI, UDP 5004 and 5005, booth network only; the installer opens them in the firewall). On the Mac with Playback: Audio MIDI Setup › Window › Show MIDI Studio › Network. In Directory press +, type the C3 Life server's address and port 5004, then Connect. In Playback, send MIDI Out to that session.
  - **What each message does:**
    - **Program Change n** on the chosen channel fires C3 Life's cue n (numbers can start at 1 or 0);
    - **a note** does Go, Back, Release, Blackout on or off, a cue, a palette preset or a look;
    - **a controller** can be the master;
    - **the MIDI clock** can set Lightkey's tempo.
  - **Only while Follow Playback is on:** turning it on asks first. Until then each message is listed with what it would have done, and nothing is sent. Lightkey's link has to be on too.
  - **Where it's kept:** `data\lights_midi.json`, through `GET/PUT /api/lights/midi` (Lights view and control).
  - **The other way:** Playback's MIDI can still go straight into Lightkey on the Mac (Lightkey › External Control › MIDI), without C3 Life.
  - **Not tried with Playback yet.** The session takes the Mac's invitation and keeps its clock in step. Lost MIDI isn't recovered (the recovery journal is ignored), so a wired network is best.

**Network scan** (Drivers › Scan the network). The C3 Life server finds the booth gear itself, so it sees the booth network even when the phone or iPad is on Wi-Fi. It sends the Wing's own search ("WING?" on UDP 2222, which the Wing answers with its name, model and serial number), asks Bonjour for Dante devices and network MIDI sessions, tries every address on the booth network (`allowed_networks`, e.g. 192.168.10.0/24) on the ports the booth apps use, asks whatever answers what it is (ProPresenter `/version`, the C3 Life helper `/hello`, Shelly `/shelly`, Companion's web page, the Tio's input 1 gain, a Shure receiver's `DEVICE_ID`), and reads the ARP table for each device's hardware (MAC) address. **A scan only asks; it never changes anything on a device.** The rules: gear it recognises that isn't set up yet, and is the only one of its kind, connects in **Watch only**; if a device that is set up stops answering and the same hardware ID (the Wing's serial number, or the MAC address) answers somewhere else, C3 Life follows it, back in Watch only if it was in Control; a scan never turns Control on; a Wing turned Off on the Mixer screen stays off; if there are two of a kind and neither is the one set up, nothing changes and Drivers asks which one (*Use this one*); everything else that answered is listed under **No driver yet** with what's known (its name, the maker of its network card when we're sure, a web page title), and an Admin can *Add as a driver* or mark it *Not booth gear*. It scans by itself 20 seconds after start-up and every 5 minutes (an Admin can turn that off, or set `"scan_auto": false`). It takes about 10 seconds. Kept in `data\scan.json`. The ProPresenter port probed is the one in `"propresenter"`. Not recognised automatically yet: Lightkey and the Sennheiser receivers (they need a driver added by hand). **Not tried on the church network yet.**

**Hardware check** (`server\hwcheck.py`, steps in `HARDWARE-CHECK.md`). Before the HP arrives, run it from any Mac or Windows laptop on the booth switch (`python3 hwcheck.py`). It runs the network scan, then watches the Wing and the Tio for 20 seconds each with the same code the C3 Life server uses, in Watch only, and reads ProPresenter's version. It refuses to send anything that would change a device: a Wing message with a value, or a Tio line that isn't a `get`. It writes `hwcheck-report-<date>.txt` to send back. It's also installed next to the server, for the HP later.

**The WING look.** Every screen looks like WING Edit: near-black, panels with thin outlines, boxed yellow page titles, condensed labels and buttons, yellow for what's active and blue for what's selected. On iPads held sideways and laptops (1000 px and wider) the menu is a left sidebar with icons, like WING Edit's. It's one block of CSS applied to every screen by the same script, so it can be changed in one place. *Change user › Look on this device › Classic* puts the earlier look back on one device (the accent colour stays yellow).

**Mix sync.** When someone signs in on a phone or iPad, C3 Life on the C3 Life server checks their PIN. It then keeps their saved mixes and own mix the same on every device they're signed in on, within about 4 seconds. Each person can turn this off in My mix › Settings.

You can run any script again safely. `Setup-C3LifeServer.ps1` only changes what isn't already right. `Install-C3Life.ps1` keeps your `config.json`.

## Options

```powershell
.\Setup-C3LifeServer.ps1 -UpdateMode Off          # no automatic updates at all (default: Notify)
.\Setup-C3LifeServer.ps1 -AdapterName "Ethernet"  # if it picks the wrong network port
.\Install-C3Life.ps1 -NoKiosk                # don't open C3 Life full screen at sign-in
.\Install-C3Life.ps1 -NoSubtitles           # don't install Vosk or the speech model
.\Install-C3Life.ps1 -Languages es,fa,zh    # translated subtitles in Spanish, Persian and Chinese (default: es)
.\Install-C3Life.ps1 -SpeechModel <zip url> # a different Vosk model (bigger = more accurate, slower)
.\Uninstall-C3Life.ps1 -RemoveData           # also delete logs and config
```

## Changing the sound desk

C3 Life talks to the sound desk only through a **desk driver** (`server\desk.py`). The Behringer Wing is the first driver (`server\wing.py`).
- **Choosing one:** `config.json` picks it with `"desk"`: `"wing"` (the default) or `"none"`. With `"none"`, C3 Life runs without a desk: the Mixer and monitor mixes say the desk can't, and everything else (Listen, Show, Lights, the room-mic RTA, Chat...) works.
- **Adding another desk** (an Allen & Heath dLive or SQ, a Yamaha CL or DM7, a Behringer X32...) means writing one driver with the methods listed at the top of `desk.py`:
  - connect, Watch only or Control;
  - names, faders and mutes;
  - sends to buses, a bus's EQ, and channel processing;
  - preamps, meters, the desk's RTA, output patching, and finding it on the network.

  It says what it can do in `CAN`, and answers anything it can't in words. The screens, access levels, monitor mixes, cues, the RTA and Lights stay as they are, and so do the `/api/wing/...` addresses the screens use.
- **The check:** `server\test_desk.py` makes sure every driver has the whole interface, and that C3 Life runs with no desk.
- **Still Wing-only:** the hardware check (`hwcheck.py`) and the Wing's own patch screens. The screens still say "Wing" in places.

## What the scripts don't do

- **BIOS settings.** Windows can't change them. See guide Step 1.
- **Automatic sign-in.** Use Sysinternals Autologon, which stores the password encrypted.
- **Installing Dante Controller, DVS, R Remote or Companion.** They need your accounts and licences. The installer only checks they're there.
- **Wi-Fi for internet.** Join the church Wi-Fi yourself.
